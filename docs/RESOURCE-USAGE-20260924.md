# R7 修正與資源用量量測 — 2026-09-24

## 結論

R7 已修正。相同數值的新樣本會推進系統匣迷你曲線，舊尖峰能正常移出；
視窗內容完全相同時仍重用 HICON。Release 建置 0 警告／0 錯誤，45/45 回歸群組通過。

本次正式量測的平均 CPU 為 0.072–0.139%（全機 16 個邏輯處理器正規化）。
此條件下沒有證據顯示需要優先做 CPU 微調。關閉視窗後仍有資源保留，下一步應先驗證
重複開關是否持續增長，尚不能定性為洩漏。

## 正式量測條件

- 量測基底為 main `941f6b2`（v1.3.0），加上當時尚未提交的 R7 修正；此修正納入 v1.3.1，版本更新未改變量測邏輯。
- Windows、非系統管理員、.NET 10.0.12、16 個邏輯處理器。量測工具與正式程式的 GC/PGO 設定已逐項比對：workstation GC、Concurrent=false、ConserveMemory=5、TieredPGO=true。
- 使用真正的 WinMonitorContext、感測器輪詢與 WinForms 視窗；38 個 descriptors，選取有回報值的 CPU Load 加 3 條 CPU Power。1 秒輪詢、1 個啟用迷你曲線的系統匣圖示、1 分鐘圖表。
- 啟動先暖機 20 秒；每個狀態再暖機 10 秒、量測至少 30 秒，每秒取樣。第一輪依系統匣→主視窗→圖表→診斷頁，第二輪反序。切換狀態會關閉舊視窗，符合 close-to-tray。
- 使用獨立設定目錄，停用測試宿主的開機啟動註冊、全域快捷鍵與啟用管道；一般程式的預設行為未變。量測期間不強制 GC，取樣開銷包含在程序用量內。

CPU 定義：程序 CPU 時間增量 ÷ 實際經過時間 ÷ 16 × 100。
記憶體列為各區段的中位數；私有記憶體與工作集不是同一指標。

這不代表非提權環境可讀取全部 EC/MSR/SMART 指標。

兩輪在同一程序內執行，沒有強制清除快取，因此第二輪記憶體包含前面場景留下的快取／配置。
表格不是各視窗「獨立增加」的記憶體，也不是修正前後的 CPU 比較。測試使用一般桌面背景活動，
沒有產生壓力負載。不同場景的微小 CPU 差異不應視為確定的瓶頸排名。

## 計時後的資源保留診斷

此操作只在所有正式取樣結束後進行，未加入正式程式或一般量測策略：

| 指標 | 強制完整回收前 | 完整回收／finalizers 後 |
|---|---:|---:|
| 私有記憶體 MiB | 66.1 | 68.1 |
| Managed heap MiB | 6.32 | 1.96 |
| GDI objects | 47 | 45 |
| USER objects | 40 | 40 |

回收使 managed heap 下降，但私有記憶體没有同步下降，GDI 仍高於冷啟動的 30。
這只能確認「有資源保留」，無法單靠兩輪區分固定快取、仍被參考的物件與洩漏。
建議下一輪做固定次數的開關視窗壓測，觀察是否達到平臺，再決定要修改哪個釋放路徑。

## R7 行為證據

原程式在新測試中失敗：相同數值的 32 次取樣應合併成 1 次 UI 更新，實際為 0。
修正後測試確認：

1. 80 → 40 → 持續 40 的序列，超過 32 筆後不再保留舊尖峰。
2. 平坦且相同的歷史視窗重用 HICON。
3. 數字-only 圖示仍略過相同數值的 tick。
4. 自動選取感測器可正常推進歷史。
5. 空 snapshot／未改變的無關感測器不增加重繪工作。
